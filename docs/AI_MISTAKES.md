# AI mistakes log

Real entries only. Write each one when it happens, not afterwards. If nothing
went wrong, leave the table empty rather than inventing an entry: an
interviewer will ask for the details.

| 2026-11-07 | Live end-to-end check through `/chat` with DeepSeek (OpenRouter): a teacher buying $1,500 of books, and a nurse buying $2,000 of gear | The tool returned the right figures in cents (130000), but the model converted them to dollars wrongly: it wrote "you'd pay $130.00" instead of $1,300.00 (wrong in at least 3 of 9 book replies, plus one that wrote $130.00 and then corrected itself), and "$4.90" cash back instead of $49.00 (2 of 6 gear replies). Smaller carts were fine. | A keyword check for "$1,300.00" failed in the first run; repeating the question and reading the replies showed where the amounts went wrong | Tool results now carry ready-made dollar strings (a `dollars` object and `annual_cap_dollars`, built with integer math in `app/money.py`) next to the cents; the prompt says to quote them exactly and no longer has a cents-to-dollars example the model could misapply. Added tests, including a parse-back check for thousands of values, and evals q9 and q10 that forbid the exact wrong amounts. After the change, 27 of 27 live replies had only amounts the tools returned, including 12 of 12 for the two cases that failed before | Never let the model convert units: give it the final string. Re-run a live money check (repeat runs, any amount not from the tools counts as wrong) after any prompt or tool change |
| 2026-11-07 | A live battery of 20 odd prompts (out of scope, injection, other members, odd amounts, other languages) | Four things the keyword flags did not all catch: it answered a Chinese question in English; it read "-$50" as a $50 cart without asking; it added $19.99 and $5.01 itself although the prompt says never do arithmetic on money (the sum was right); and it priced a $99,999,999,999 cart because the tool had no upper limit while the web API did | Reading all 20 replies: the heuristic flags caught only 2 of the 4 | Prompt: answer in the member's language, and ask for one cart total when an amount is zero, negative, unclear or several. One shared cart limit ($1,000,000) for the tool and the web API. Tests for each. Re-run live: all four fixed, and 27 of 27 money replies still correct | Read the answers, not only the flags. After any prompt change, re-run the live battery and the strict money check |
| 2026-11-08 | A live check (13 runs) of what the concierge lists, with a member and no store chosen: "Show my best deals" (and later the chip's own text, "What are the best discounts I qualify for?") | In 4 of 5 runs of "Show my best deals" (also for the member with no verified group) it asked "which store?" and called no tool. The one good run looked every store up with six parallel calls. The question has an obvious meaning and the model treated it as missing information, because the only tool that lists a member's offers needs a store id. | My own live script flagged "no link" and "date missing" on those runs; I then read the replies. | Tests first, then a read-only tool `list_all_eligible_offers` (no arguments, bound to the session member, largest percentage first, no third-party terms text) and a prompt rule that says to call it and not to ask which store. | When a common question has an obvious default meaning, give the model a tool that answers it in one call instead of hoping the prompt makes it improvise six. Measure it live afterwards: 2 runs of 20 (2 phrasings, 2 members, 5 each), 40 of 40 called the tool and listed valid links. My first checker marked 4 of the first 20 as "asks which store" by mistake: they were the closing offer "tell me a store and a cart total" that the prompt asks for; I fixed the checker, not the model. One model, one day: not a pass rate. |
